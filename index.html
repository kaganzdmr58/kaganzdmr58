How I work

  1. Understand the problem before writing code

    I start from the requirement and the constraint, not from the framework. Many of the projects below exist because someone described a manual process and I turned it into software.

  2. Choose the right stack, not my favourite stack

    Flutter when one codebase should serve both platforms. Native Kotlin or Swift when the platform fights back — and I write those packages myself rather than hunting for a pub.dev approximation. PHP or Python on the backend depending on what the client already runs.

  3. Design the architecture up front

    Clean Architecture, MVVM, modular packages, repository pattern, dependency injection. On a shared codebase serving 26 branded apps, a weak architecture is not a style problem — it is an outage.

  4. Test it, ship it, watch it

    Unit, widget and integration tests; CI/CD with GitHub Actions and Fastlane; signing, versioning and store submission automated; Crashlytics and performance monitoring after release, because a profile build on my own machine never reproduces what the slowest 10% of users experience.

  5. Own it after launch

    Everything listed here went to production and stayed there.
